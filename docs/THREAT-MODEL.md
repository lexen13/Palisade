## 0. How to read this

This is the adversary's view of Palisade: what is worth attacking, who can attack it, where the
attacker's bytes cross into the program's trust, and what stands at each of those crossings
today. It is deliberately narrow. It does not restate the feature list, and it does not claim
anything the artifact cannot be made to demonstrate in front of you.

Three conventions:

- **"Control"** means a mechanism in the shipped file, named by line, not a policy or an
  intention. Each one is followed by the measurement that shows it working.
- **"Measured"** means a figure produced by running the tool or the gate against the sealed
  artifact named above. Figures marked *(measured for this document, 2026-09-11)* were re-run
  while writing it. The Chromium transcripts from that campaign are a review-workspace bundle,
  not files in this repository; the in-repo substitutes are `tools/seal.mjs --verify`,
  `tools/csp-lint.sh`, and `baseline/harness.mjs`.
- Where a control is partial, the section says how far it goes and where it stops. There is no
  section that says "fully mitigated".

## 1. The deployment picture

Palisade is a single HTML file. An operator copies it to a NIPR or air-gapped workstation —
often from a USB drive — opens it from `file://`, and drags in Tenable/ACAS exports. The page
parses them in the browser, builds RMF evidence (STIG applicability, eMASS baselines, PPSM
registry rows, POA&M drafts, account audits, asset inventories), and writes those out as
downloads. There is no server, no installer, no database, and no browser storage. When the
tab closes, the working set is gone unless the operator saved a session file.

Two consequences shape everything below.

1. **The program's only inputs are files.** There is no login, no request, no API. An adversary
   who wants to influence Palisade must get bytes into a file the operator drops in. That makes
   the file-drop the single most important boundary in the system.
2. **The program's outputs travel.** The CSV, TXT and HTML artifacts are the point of the tool.
   They leave the workstation, leave the air gap, and are opened by an assessor on a networked
   machine in an application — Excel — that executes some cell contents. That is the boundary
   most easily forgotten, and it is where the air gap actually ends.

## 2. Assets

**A1 — Integrity of the compiled evidence.** *(primary)*
An RMF package is built on Palisade's output. If a crafted scan file can change a STIG mark, a
PPSM row, a POA&M entry, or the scan-detected-versus-inventory-only flag on an asset, then the
authorization decision rests on altered evidence, and nothing in the downstream process is
positioned to notice. In a tool whose product *is* evidence, silent tampering is worse than a
crash, worse than a hang, and — in this deployment, which has no network egress — worse than
anything an injected script could do to the browser.

**A2 — CUI inside session files and evidence packages.**
A session `.json` is the complete raw dataset: every hostname, IP, MAC, software row, and
enumerated account with RID, group membership and admin flags for a real enclave. The evidence
`.zip` can carry that file. These are the most concentrated CUI the tool ever produces, and
they are routinely handed between colleagues and attached to packages.

**A3 — Availability of the operator's workstation and working set.**
The working set lives in one tab's memory. A hostile input that hangs or OOM-kills the tab
destroys an assessment cycle's manual work — device types, PPSM notes, approval records — none
of which came from a scan and none of which can be regenerated by re-running one.

Not an asset in this model: confidentiality of the Palisade source (it is MIT-licensed and
public) and availability of the tool itself (it is one file; a fresh copy is a file copy).

## 3. Adversaries

Each of the three is concrete, each is someone who really exists in this workflow, and each is
traced to the code path that carries their bytes.

### 3.1 A hostile scanned host

**Who.** A machine inside the scanned enclave that is already compromised, or is hostile by
design, and that controls what it reports to the scanner: its hostname, its NetBIOS name, its
FQDN, its service banners, its installed-software DisplayNames, its local account names — and,
in the scan record it produces, the `protocol` attribute itself.

**Why this is not theoretical.** None of those fields is validated by the scanner. Tenable
records what the host said. The operator then drops that file into Palisade with no reason to
suspect a hostname.

**The code path.** `.nessus` ingest reads `protocol` verbatim from the report item
(`palisade.html:2054`), and `addPort()` lower-cases it and makes it half of a PPSM key —
`const k=proto+"/"+port` (2015). That key is an object key in `S.ppsm`, and the PPSM renderer
writes it into the per-row controls (5026-5046). Host keys take the parallel path through
`hostKeyFrom()` (1873) into the STIG renderer (5113-5128).

In v2.7 both renderers interpolated the key *raw* into a JS string inside an `on*=""` attribute.
A protocol value of

```
tcp"><img src=x onerror="document.title='PWNED';window.__pwned=1">
```

therefore executed on drop, with no click. Measured for this document against the pristine v2.7
build (`pristine/palisade-v2.7-ORIGINAL.html`, sha256 `8918858e…`), `fixtures/hostile.nessus`:

```
title: "pwned"   (baseline "Palisade v2.7")   window.__pwned: set   injected <img>: 16
==> CANARY FIRED (FAIL)
```

Same probe, same fixtures, against the sealed v2.8 artifact:

```
hostile.nessus / hostile-session.json / hostile-session-xss.json / hostile.csv
title unchanged   window.__pwned: undefined   injected <img>: 0   csp violations: []
==> HOSTILE PROBE: PASS
```

*(both measured for this document, 2026-09-11, `baseline/hostile-probe.mjs`, Chromium
150.0.7871.181, real `file://`)*

**What this adversary is after.** Not the workstation — there is nothing to exfiltrate to. The
prize is A1: script running inside the page can rewrite the marks, rows and counts that become
the RMF package, and the operator sees a normal-looking table.

### 3.2 A colleague's shared session, profile or baseline JSON

**Who.** Not necessarily malicious — this is the *misplaced trust* case. Session files,
environment profiles and baselines are swapped between team members as a matter of routine:
"here's last month's baseline", "here's the profile for that enclave". The file arrives over
chat, email or a share, and the receiving operator loads it without thinking of it as input.

**Why it matters more than the scan path.** A scan file's hostile content is constrained by what
a host can plausibly report. A hand-crafted session file is constrained by nothing. It controls
object *keys*, value *types*, and the detection-config regexes the tool will compile and run.

**The code path — three distinct primitives.**

1. **Object keys into renderers.** `loadSession()` (7265) does `S=Object.assign(newState(),obj)`,
   then renders. Every key in `S.ppsm`, `S.hosts` and `S.software` is attacker-chosen text.
   `fixtures/hostile-session-xss.json` carries the PPSM key
   `x"><img src=x onerror="document.title='PWNED';window.__pwned=1">/443`. Measured against
   pristine v2.7: `title "PWNED"`, 14 injected `<img>`, canary fired. Against v2.8: canary
   silent, 0 injected, 0 CSP violations *(measured for this document)*.

2. **Global prototype pollution — finding R3, and the one this model treats as the most
   dangerous of the three.** `JSON.parse` creates a genuine *own* `__proto__` property, but a
   later read of `map["__proto__"]` goes through the prototype getter and returns
   `Object.prototype`, which is truthy. `buildAssets()` (4730) enumerates with `for..in` and
   tests `if(!S.assets[hk])`, so that key took the *refresh* branch and wrote `fromScan`, `ip`,
   `os`, `lastSeen` and `type` onto `Object.prototype` itself. Every object in the page then
   inherited `fromScan===true`, so the second loop's test —
   `if(!S.hosts[k]&&S.assets[k].fromScan===undefined)` (4750-4752) — stopped firing, and assets
   that produced no scan this cycle stopped being marked as such. The scan-detected versus
   inventory-only distinction inverts silently, and it feeds the asset inventory, the
   reconciliation view and the readiness meter. Measured (`evidence/gate-B/verify-B.txt` §8):
   pristine gains `fromScan`/`type` on `Object.prototype` and `({}).fromScan===true`; hardened
   shows `Object.prototype` own props 12 before and 12 after, polluted keys `[]`,
   `({}).fromScan===undefined`, and the prior dataset intact at hosts=6, ppsm=19, stig=8, sw=24,
   asset=9. Note what this defeats: restoring `S` from a backup does not undo it, because the
   write outlives the state object. It had to be stopped at the JSON boundary.

3. **Config-supplied regexes.** A profile can set `catalog[*].patterns`, `osPatterns` and
   `productAliases` to `re:` strings that Palisade compiles and runs against scan text
   (`patMatch()` 1710). `re:(a+)+$` against a long subject hangs the tab.

**What this adversary is after.** A2 and A1 together: a shared file is the highest-trust,
lowest-friction way to reach the state object, and R3 shows it can change what the evidence
*means* without changing a single visible row.

### 3.3 A hostile value reaching a spreadsheet on the assessor's networked machine

**Who.** The same hostile host as §3.1, but the target is not the operator. It is the assessor,
the ISSM, the validator, or anyone else who opens the evidence CSV — on a networked machine,
in Excel, downstream of the air gap.

**Why this is the boundary that matters most and is forgotten first.** Everything protective
about this deployment — offline, no egress, controlled workstation — stops at the moment the
`.zip` is handed over. The recipient's machine has none of those properties, and Excel and
LibreOffice execute a cell that begins `=`, `@`, TAB or CR: DDE, `WEBSERVICE()`, `HYPERLINK()`.
A hostname of `=CMD|'/C CALC'!A0` recorded by the scanner is written into the evidence by
Palisade, and fires on someone else's desk, days later, where there is a network.

**The code path.** Attacker-influenced values reach cells in every export: `i.host` (hostnames),
`r.product` and software names/versions, `a.name` and `a.groups` (enumerated accounts). In v2.7
`csvq()` quoted per RFC 4180 only and `tsvSafe()` flattened whitespace only; neither neutralised
a leading trigger character.

**Measured** (`evidence/gate-B/verify-B.txt` §1, v2.8):

| fixture | exports captured | cells still live | cells neutralised | numeric controls |
|---|---|---|---|---|
| `hostile.csv` | 19 | **0** | 43 | `-5`, `+5`, `-5%` all bare, 0 prefixed |
| `hostile-session-xss.json` | 19 | **0** | 27 | `-5`, `+5`, `-5%` all bare, 0 prefixed |

A neutralised cell arrives as `'=CMD|'/C CALC'!A0` — text, with a visible apostrophe. That
apostrophe is deliberate and is a behaviour change worth telling recipients about: unlike a
typed-in leading quote, CSV import shows it. A value that needed neutralising is worth seeing.

**What this adversary is after.** Code execution on a networked machine, using the evidence
package as the delivery vehicle and the assessor's own trust in it as the exploit. Severity is
adjudicated **medium**, not high: it needs the recipient to open the file, modern Excel prompts
before DDE, and the payload runs on the recipient's machine, not the air-gapped one. It is
listed here because the impact lands outside the boundary everyone else is defending.

## 4. Trust boundaries

**B1 — Drop zone → parsers.** The `drop` listener (1822) and eight `<input type="file">`
elements (452-922) hand raw bytes to `ingestFiles()` (1824). Everything upstream is untrusted;
everything downstream assumes structure. Resource limits belong here, because this is the last
point at which nothing has been allocated yet.

**B1b — The JSON boundary.** Seven call sites take JSON that came from a file or a textarea:
`loadSession` (7265), `ingestTrendSessions` (4538), `loadBaseline` (4699), `loadProfile` (7610),
`applyConfig` (7189, the detection-config box), and the `.cklb` sniff and parse (5830, 5833).
This is a *separate* boundary from B1 because JSON does not merely carry values — it carries
keys, types, and, via `__proto__`, a handle on the language itself.

**B2 — Parsers → the `S` state object.** Past this point the data is in plain JS objects and
looks like program data. It is not: the *keys* are still attacker-influenced text. Any code that
assumes a key is a well-formed identifier — or that a lookup returns own data — is wrong here.

**B3 — `S` → renderers → DOM.** Values and keys become markup. This is the classic injection
boundary and the one v2.7 got wrong twice.

**B3b — The `srcdoc` preview frame.** `#rptPreview` (1007) receives generated report HTML built
from scan-derived values (4434). It is a document inside the document.

**B4 — `S` → exports → other people's machines.** The largest boundary in the system, because
what crosses it executes inside someone else's application, on hardware this model does not
control, after the artifact is out of anyone's hands.

## 6. Sink classes, the control, and how each is verified

### 6.1 Markup / attribute injection at the renderers (B3)

**Sink.** An attacker-controlled object key or value interpolated into generated HTML.

**Control.** Two mechanisms, both in the shipped file.

- `esc()` (1765) entity-encodes `& < > " '`; the token `esc(` occurs **344** times in the
  shipped file — **343** call sites plus the definition itself at 1765 *(measured 2026-09-11,
  `grep -oE '\besc\(' palisade.html | wc -l`)* — covering text and quoted-attribute contexts.
- Keys no longer travel inside JavaScript at all. Each of the **19** `data-key=` sites carries
  `esc()`'d text (`${esc(k)}`, `${esc(hk)}`, or `${ke}` where `const ke=esc(k)` at 5209/5343),
  and the value is read back from `el.dataset` as a string — **one** encode, **one** decode,
  no second parse. The v2.7 idiom `JSON.stringify(x).replace(/"/g,"&quot;")`, which a literal
  `&quot;` in the data defeated, does not appear in the file.

**Verified by.** The hostile-fixture probe, four fixtures, canary `document.title` plus
`window.__pwned` plus a count of injected `<img>`, with the generated controls actually clicked
afterwards: **PASS on the sealed artifact, FAIL (2 fixtures) on pristine v2.7** *(both runs
measured for this document, 2026-09-11)*. The equivalent run recorded during the gate is
`evidence/gate-C/06-hostile-fixtures.txt`; see §10 for why its hash differs. The round-trip
assertion matters as much as the canary: a hostile key must still *work* as a key — the probe
records `ppsm rows changed:true` and `stig toggled:true`, so the fix escapes the key without
breaking the edit it identifies.

**Compliance note.** This class maps to ASD STIG **APSC-DV-002490** (XSS, CAT I) and
**APSC-DV-002480** (CAT II). Those two V-IDs were verified during the assessment. Any other
V-ID must be confirmed against the current ASD STIG release before it is cited — do not carry
one over from another package.

### 6.2 Script execution of any origin (backstop, whole document)

**Sink.** Anything that would run as code: an injected `<script>`, an `on*=` attribute that
reached the DOM, `eval`, `new Function`, the string forms of `setTimeout`/`setInterval`.

**Control.** The CSP at line 18, quoted in full in the diagram above. Script is permitted only
by the SHA-256 of the one inline block. With a hash present the browser ignores `'unsafe-inline'`
for scripts, so an `onclick` written into the page by hostile data cannot run. Getting there
required converting 191 of the file's 192 inline handlers to `data-click` / `data-change` /
`data-input` attributes dispatched through `dispatchUI()` (7927) against the frozen `ACTIONS`
allow-list (7828). Measured on the shipped file *(2026-09-11)*: **1** inline `on*=` attribute
remains, and it is the print button written into the *downloaded* report — a separate document
with its own policy — tagged `/*EXPORT-ONLY-HANDLER*/` and checked as an exemption by
`tools/seal.mjs`. The dispatcher does **not** use `window[name]`: in a classic script every
top-level function is a `window` property, so that would have made hundreds of internals
reachable from markup.

**Verified by.** `evidence/gate-C/negative-tests.txt` — each attack primitive attempted in a
live Chromium on a real `file://` URL, with the browser's own refusal text captured:

| test | result | directive that refused it |
|---|---|---|
| `insertAdjacentHTML` of `<button onclick=…>`, then click it | refused, canary silent | `script-src-attr` |
| `setTimeout("…", 0)` — string compiled by the page | refused, canary silent | `script-src` (`blockedURI: eval`) |
| `fetch("https://example.invalid")` | refused | `connect-src` |
| `new Image().src = "https://example.invalid/x"` | refused | `img-src` |
| inject a `<script>` element into the DOM | refused, `window.__pwned` undefined | `script-src-elem` |
| `eval("1")` typed at an attached debugger | **not refused — expected, see §8.3** | (no check applied) |

And then: the page loaded the demo dataset normally afterwards (hosts=6, ppsm=19). That last
step is what makes the refusals mean something — an inert page would have "passed" every one.

### 6.3 Prototype and key-lookup abuse (B1b, B2)

**Sink.** A `__proto__` key from a parsed file reaching a `for..in` write; a `data-*` key naming
an arbitrary property of a state object.

**Control.** `safeParse()` (1775) — a `JSON.parse` reviver that drops `__proto__` — at all seven
untrusted-JSON entry points. **Zero** raw `JSON.parse` on file or textarea input remains; the
remaining `JSON.parse` occurrences in the file are all `JSON.parse(JSON.stringify(DEFAULT_CONFIG))`
deep-copies of the tool's own constants *(measured 2026-09-11: 11 occurrences, 10 of them that
deep-copy idiom, 1 the reviver itself)*. This was chosen over guarding the file's 41 `for..in`
loops *(measured)* because it is one reviewable choke point that a future renderer cannot
forget. At the dispatch
layer, `own()` / `hasOwn()` (7826) guard every key lookup and field names are checked against
the column definitions, so markup can never name an arbitrary property.

**Verified by.** `evidence/gate-B/verify-B.txt` §8: `Object.prototype` own props 12 before / 12
after loading the hostile session; polluted keys `[]`; `({}).fromScan === undefined`; and the
operator's prior dataset still on screen at hosts=6, ppsm=19, stig=8, sw=24, asset=9 after the
refusal.

### 6.4 Spreadsheet formula / DDE injection at the export boundary (B4)

**Sink.** Any scan-derived string written into a `.csv` or the PPSM registry `.txt`.

**Control.** `csvNeutral()` (7210) — one function, called by both `csvq()` (7226, used at 26
sites across the CSV exporters) and `tsvSafe()` (7211, the PPSM registry). Leading `=`, `@`,
TAB or CR is always prefixed with `'`; leading `+` or `-` only when what follows is not a plain
number, so `-5`, `+5` and `-5%` keep their numeric type and numeric columns still sum.

**Verified by.** `evidence/gate-B/verify-B.txt` §1 — the table in §3.3 above: 19 exports
captured per fixture, **0** live cells, 43 and 27 neutralised, numeric controls intact, plus a
direct probe of the choke point in the live page for 14 representative inputs.

### 6.5 The report preview frame (B3b)

**Sink.** Generated report HTML, built from scan-derived values, injected as `srcdoc` (4434).

**Control.** `sandbox="allow-same-origin allow-modals"` on `#rptPreview` (1007) — no
`allow-scripts`, so the frame cannot run script and cannot remove its own sandbox. The parent's
CSP is inherited into `about:srcdoc` regardless (empirically established before the change:
`evidence/csp-probe/RESULT.md`). `allow-same-origin` is present only because the print
button lives in the parent and needs `contentWindow.print()`; the preview document itself
carries no print handler.

**Verified by.** `evidence/gate-B/verify-B.txt` §5, measured in the live page: sandbox attribute
as specified; elements with `onclick` **0**; elements with any `on*` attribute **0**;
`<script>` tags in the preview document **0**; a script injected into the frame's document did
not run (`window.__frameRan` undefined); the preview still rendered fully styled (295 elements,
4 tables, 3,263 chars of CSS applied). It renders, and it is inert.

### 6.6 Resource exhaustion at the parsers (B1) — asset A3

**Sink.** `zipOpen().read()` inflating a deflate stream; unbounded XML row extraction; unbounded
file reads.

**Control.** `LIMITS` (1794), named and frozen so a program can cite them and an integrator can
tune them: 1 GiB per input file (checked *before* the file is materialised), 256 MiB per
inflated zip entry, 768 MiB per archive, 1,048,576 sheet rows, 512 chars of regex source. The
inflate cap is the only one of these that is a mitigation rather than a stated bound — deflate
amplifies about 1032:1, so a few hundred KB can reach gigabytes. Every breach surfaces as a
named refusal in `#parseWarnings` (1863); none is a silent truncation.

**Verified by.** `evidence/gate-B/verify-B.txt` §2-3:

| | pristine v2.7 | v2.8 |
|---|---|---|
| `bomb.xlsx`, peak RSS delta | 2,573.0 MiB, **silent success** (empty warning banner) | 329.8 MiB, banner names the limit |
| `bomb.zip`, peak RSS delta | — | 304.5 MiB, banner names the limit |

That last row is the one that matters for a control like this: a limit that refuses real ACAS
exports is a worse defect than the bomb it was meant to stop.

### 6.7 ReDoS from configuration regexes (B1b)

**Sink.** `re:` patterns in a detection config or environment profile, compiled at 1710 and run
against scan text.

**Control.** `unsafeRegexSource()` (1688) rejects the classic nested-quantifier shapes and any
source longer than `LIMITS.REGEX_SOURCE_CHARS`, at construction. Rejections are reported by name
in the status line rather than silently dropped.

**This control is partial, and the partiality is the honest part.** It catches `(a+)+`, `(a*)*`,
`(\d+)+`, `((ab)+)+` and over-long sources. It does **not** catch adjacent overlap (`a*a*$`) or
alternation overlap (`(a|ab)*`) — both were deliberately kept in the fixture as *accepted*
controls so the transcript shows the gap. Subject-length bounding gives no protection
(exponential patterns hang at ~30 characters) and a synchronous regex cannot be time-bounded in
a `file://` page, so static rejection is the only portable control available here.

**Verified by.** `evidence/gate-B/verify-B.txt` §4: all **32** built-in `re:` patterns walked,
**0** rejected (a validator that rejects the tool's own catalog is useless); the hostile profile
produced 6 rejections, named in the status message; detection completed in 0 ms afterwards.

### 6.8 CUI over-distribution (asset A2)

**Sink.** The evidence package, and the repository.

**Control.** The resume-session file in the package is **opt-in, default off** (`#pkgInclSession`),
and `index.html` carries a caveat sentence either way — naming the file as the complete raw
dataset when it is present, saying it is absent when it is not. In the repository, the
CUI-protection ignore file shipped as `gitignore.txt`, which git never reads, so every rule in
it was dead text — including the block meant to stop `*.nessus`, `session*.json`, `*.ckl` and
`Results_*.zip` being committed (finding R1). It is now `.gitignore` and live.

**Verified by.** `evidence/gate-B/verify-B.txt` §7: box unticked → 22 zip entries, **0**
`Palisade_Session_*`, index says "No resume session file is included"; box ticked → 23 entries,
1 session file, index carries the "complete raw dataset" warning.
`evidence/gate-C/07-repo-hygiene.txt`: the ignore rule resolves, and a history search for
`*.nessus`, `*Session*.json` and `*.ckl` returns nothing — no scan data was ever committed.

### 6.9 Integrity of the file itself

**Sink.** The copy on the USB drive, or on the share, or on the workstation — edited in transit
or at rest.

**Control.** The script-block hash in the CSP is a seal, not a checksum. Any edit to the script
— one byte, including whitespace — invalidates it, and the browser refuses to run the script at
all.

**Verified by.** `evidence/gate-C/05-tamper-evidence.txt`: one byte changed inside a *comment*
in the script block (offset 83048, `a`→`X`, behaviour unchanged). Sealed copy: script ran,
demo load gave hosts=6, ppsm=19. Tampered copy: `appDefined:false`, `dispatchWired:false`, 0
table rows, `S is not defined`, and the browser's own message naming both the expected and the
actual hash. The page still rendered its markup and stylesheet (782 DOM nodes, correct
background) — visibly Palisade, visibly not working. That is a useful failure mode: it does not
depend on anyone choosing to run a checksum, and the expected hash in the console can be
compared against `SHA256SUMS` with no Palisade-specific tooling.

## 7. Residual risk — what these controls do not reach

**7.1 `style-src 'unsafe-inline'` remains.** The file sets 483 `style=` attributes, about a
hundred of which carry a runtime value (measured 2026-09-11 on the shipped build: 49
template-literal interpolations, 53 built by string concatenation). Note that the file's own
CSP comment (line 15) still reads "481 style= attributes" — a figure carried over from an
earlier build and frozen in place by the seal. 483 is the measured value; the comment is
stale and cannot be corrected without re-sealing. CSS cannot execute, and every channel that
could send anything anywhere — `img-src`, `font-src`, `connect-src`, external stylesheets — is `'none'`, so the
practical exposure is narrow. It is still the loosest directive in the policy, and hashing the
stylesheet elements is a deferred step, not a completed one.

**7.2 The ReDoS validator is partial.** §6.7. A colleague's profile carrying `a*a*$` will be
accepted and can still hang the tab. That is a working-set availability loss (A3), not an
integrity loss.

**7.3 CSP does not sanitise markup.** An injected element is still created in the DOM; it simply
cannot execute. A hostile value can therefore still make a table row *look* wrong even where it
cannot *be* code. The escaping at the renderers is what addresses that, and it is the layer that
carries the weight — the policy is the backstop.

**7.4 The seal makes any edit fatal, including a legitimate one.** `node tools/seal.mjs
palisade.html --seal` is mandatory after any change to the file, or the page is inert. This is
documented as an operating constraint rather than softened, because it is the same property that
produces the tamper evidence in §6.9.

**7.5 `rptTable` / `rptLead` still accept raw cell markup.** A number of their 32 call sites
*(measured)* deliberately pass markup — tag and scope chips, `<span style>`, the package index's
`<a href>` — so escaping every cell by default would render those tags as visible text. All 20
report section builders were traced and every scan-derived value reaching them is escaped
today, and after the policy lock the report is contained by CSP in both the preview and the
export — so this is a hardening opportunity, not a live defect. It is named here so it is not
discovered later and mistaken for one.

**7.6 Everything downstream of the handover.** Once the `.zip` leaves, Palisade's controls end.
`csvNeutral` makes the cells inert; it does not make the recipient's handling of CUI safe, and
it does not follow the file.

## 8. Non-goals — stated plainly

These are outside the model. They are listed so that an assessor knows they were considered and
excluded on purpose, rather than missed.

**8.1 Network exfiltration.** There is no network egress path from this page, and the model
does not defend one because there is not one to defend. Measured on the shipped file
*(2026-09-11)*: **0** occurrences of every primitive that could open one — `fetch(`,
`XMLHttpRequest`, `WebSocket`, `sendBeacon`, `new Image`, `EventSource`, `new Worker`; **0**
of every storage API (`localStorage`, `sessionStorage`, `indexedDB`); **0** `<img`, `<link`,
`<form` or `<base` elements; and **0** `http://` or `https://` references of any kind. (Also
**0** `eval(`, `new Function` and `document.write`, which matter for §6.2 rather than here.)

On top of that absence, `connect-src 'none'` and `img-src 'none'` were observed refusing a
live `fetch()` and a live image beacon (§6.2). The claim is therefore browser-enforced rather
than code-reviewed: it does not depend on nobody ever adding a `fetch()` later.

What that does **not** cover, and should not be read as covering: downloads, the clipboard and
printing are not governed by CSP and keep working by design — data leaves this tool by explicit
operator action, which is the entire point of it. Nor does it say anything about the assessor's
machine after the artifacts arrive (§3.3).

**8.2 Browser and platform vulnerabilities.** Palisade runs inside the browser's sandbox and
inherits its security posture. A defect in Chromium's HTML parser, JavaScript engine, zip or
image handling, or in the OS underneath, is out of scope for this document and is covered by the
workstation's own patching and STIG compliance — it is not something a single HTML file can
mitigate. The model assumes a patched, STIG-compliant browser on a STIG-compliant workstation.

**8.3 A user who pastes hostile content into DevTools.** Out of the model — and the reason is
worth spelling out, because **an assessor re-running the negative tests will see this result and
must know it is expected.**

`eval("1")` typed at an attached debugger is **not** refused by the CSP. Chromium exempts
debugger-originated evaluation from CSP by design, so that a page with a strict policy remains
debuggable. No violation event fires, because no violation occurred: the browser did not apply
the check. This is captured verbatim in `evidence/gate-C/negative-tests.txt` (Test 2) rather
than quietly dropped.

It is a property of the debugger, not a hole in the policy. The same compiler reached from a
call site *inside* the page — which is what hostile input actually has — **is** refused:
`setTimeout("window.__evalCanary=1", 0)` produced a `script-src` violation with
`blockedURI: eval` and the canary stayed undefined (Test 3). An adversary in this model supplies
hostile *bytes* — a scan file, a session file, a hostname — not an attached debugger session.
An operator who opens DevTools and pastes attacker-supplied JavaScript into it has already
stepped outside anything the file can control, in the same way that an operator who runs an
attacker's `.exe` has.

**8.4 A malicious operator.** Someone authorised to run Palisade can already read the scan data
it parses and can export it at will. This model defends the evidence against *inputs*, not
against the person holding the keyboard.

**8.5 Anything not claimable from this artifact.** For the avoidance of doubt, nothing in this
document should be read as asserting: a filed CISA Secure Software Development Attestation Form
(not required for freely obtained OSS under OMB M-23-16); browser-verifiable code signing of an
`.html`; a reproducible or hermetic build (there is no build); a WCAG conformance level; or a
DoDIN APL listing (APL covers UC network infrastructure and is not an RMF authorization).
