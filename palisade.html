The whole process, start to finish — read this once

1. In SecurityCenter, open Scans → Scan Results, select the completed scan, and use Download to get the .nessus file. The CSV/PDF options on the report side truncate plugin output — the Download button on scan results is the one you want. If you must use CSV, include the Plugin Output column when customizing export columns, or software detection will be empty.

2. Load one or more exports here. Hosts, open-port evidence, and installed-software evidence merge across files; re-loading a newer scan updates hosts in place without wiping your edits.

3. Fill in Enclave Settings once (registration form static fields + boundary defaults). Review the PPSM Matrix rows, exclude anything not being registered, and edit boundaries per row where needed. Review STIG Applicability auto-marks and toggle cells where the scan evidence is wrong — manual overrides show a dashed amber outline and survive re-detection.

4. Export: PPSM produces the tab-delimited .txt in the exact DoD IS Registration Form v8.0 column order (paste-ready / registry-upload format). STIG produces a CSV matching the STIG Testing Matrix layout (version header row + product row + one row per host).

5. Save session writes a JSON sidecar of everything (parsed evidence + your edits) so a half-completed matrix can be handed to a teammate and resumed. Sessions and exports inherit the banner marking from Enclave Settings.

Stage 2 · Evidence

PPSM Matrix

Every port found listening on your hosts, shaped into the DoD IS Registration layout. Exclude what you are not registering, set the boundaries, then export.

PPSM exports

Noise filter

Windows assigns transient RPC ports from the dynamic range; those are not registrable services and typically account for most of the rows. Excluded rows stay visible and can be re-included individually.

Scope note — what this export is and is not

This tab shows what the scans can prove: ports observed listening on enclave hosts. Registration decisions — which flows cross which boundary, and what gets submitted — are an ISSM/ISSO call. Treat the export as evidence to hand up, not a finished registration. Note also that scan evidence only shows listening services; required outbound flows (NTP upstream, syslog forwarding, the vulnerability scanner reaching targets) will not appear here and still need to be accounted for.

Rows are unique protocol/port tuples evidenced by the scans (listening services + finding-attached ports). Direction evidence from network scanning is inbound-listen; boundary applicability is human judgment — set defaults in Enclave Settings and override per row. Notes are working-copy only and never exported to the registry .txt.

Stage 2 · Evidence

Asset Inventory

One row per asset — the hardware inventory. Scan-derived fields refresh every time you load new scans; everything else you fill in once and it sticks.

Add to the inventory
What belongs here, and why the manual entries matter

One row per asset. Name, IP, MAC, OS, device type, and last scan date are pulled from scan evidence and refresh each time you load new scans. Manufacturer, model, serial, location, owner, status, and criticality can't come from a scan — fill those once and they persist in the session file.

Assets that exist but never scan (powered-off spares, standalone media stations, network gear outside scan scope) won't appear on their own. Use Add asset not detected by scan so the inventory reflects reality rather than only what the scanner can see — those entries are exactly what makes the Reconciliation tab useful.

Stage 2 · Evidence

Account Audit

User accounts the credentialed scans enumerated — who exists on each host, who is privileged, and which accounts sit in exception states. Supports control AC-2.

What this proves, and why it can come back empty

User accounts enumerated by credentialed scans — Windows local/domain users, group memberships, and the account-state plugin family (passwords never expire, never logged on, disabled), plus Linux user enumeration. This is scan-evidenced ground truth to reconcile against the Account Management Plan: every row here should map to an authorized account, and the flags are the exceptions worth explaining.

Scan policies must include the user-enumeration plugin families (Windows "User management" and SSH user enumeration) for this tab to populate — if it's empty on a credentialed scan, check the policy before assuming there are no findings.

Stage 2 · Evidence

STIG Compliance

Actual per-rule results from SCC or STIG Viewer checklists. Applicability says which baselines apply; this says which checks pass.

STIG result exports
Where these results come from, and what Coverage catches

Actual per-rule assessment results from SCC (SCAP Compliance Checker) XCCDF output or STIG Viewer checklists (.ckl / .cklb), including zips of either. Where the STIG Applicability tab records which baselines apply, this records which checks pass — with V-IDs, STIG IDs, CAT severities, and CCI references carried through to the exports.

Checklists also carry the manual review results that no automated scan can produce, so a host assessed by SCC alone will show those rules as Not Reviewed until the checklist is imported. The Coverage view compares what the applicability matrix claims against what was actually assessed — a STIG that applies but was never run is invisible in either artifact alone.

Why this tab comes first

Every other artifact in this tool rests on the scans having actually authenticated. This tab reports what the scan says about itself: whether credentialed checks succeeded, which policy ran, how old the plugin feed was, and when it ran. An assessor asking “how do you know this inventory is complete?” is asking for this page.

Reconciliation

Compares your authoritative asset list against what actually scanned, so you catch assets that failed to scan or turned up unexpectedly.

Authoritative asset inventory

Paste your asset list — one per line, or Hostname, Type, Note if you want the extra columns. A header row is ignored. This is compared against what the scans actually found.

This list should come from outside the scan data. What the four lenses are, and what each output is for

The same evidence, cut four ways for decision-makers: Quick strikes (weaponized, confirmed on the network — act this week), Low-hanging fruit (one update clears many endpoints), Engineering campaigns (OS upgrades and fleet migrations that need planning and change control), and Modernization (unsupported components as budget-line items). Detection Config

The detection engine’s rules, in editable JSON. Tune it as STIGs release and your environment changes — no code edits, no re-download.

Field-by-field reference for every key in the JSON below

remedyWeights: how much risk one finding instance retires when its fix is applied — this is what the Remediation Plan ranks on, so an enclave tasked only on Critical/High can zero sev2/sev1 here. productAliases: merges the several ways scanners name one product (a RHEL check says firefox, the Windows plugin says Mozilla Firefox) for the Software Summary view only — the remediation plan keys on the un-aliased product, so an alias can never claim one patch covers two products that need different fixes.

catalog: master list of STIG-mapped products in export order — name, ver (STIG version shown in the header row; blank renders as ver? until you fill it from the current DISA quarterly release), active (whether it's a matrix column now), patterns (case-insensitive substrings matched against OS string + installed-software output + fired plugin names; prefix a pattern with re: to use a regular expression instead, which is how the RHEL and Windows Server entries cope with scanners reporting a version token mid-string), and optional osPatterns (OS string only). Inactive entries auto-activate the first time scan evidence hits them on any host. noisePatterns: installed-software lines to suppress from the unmapped review list. vendorRules / typeRules: first-match-wins prefill for the Software Listing's Vendor and Type columns. deviceRules: hostname-prefix → device type. listingAliases: header-name aliases for HW/SW baseline listings — add the headers your listings use and re-load, no code edits. Maintain this as STIGs release/sunset — no code changes needed.
